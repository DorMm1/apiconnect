1. Why this exists — the problem and the three decisions

Publishing APIs to API Connect by hand — editing drafts in API Manager and pressing Publish — works for one team and a handful of APIs. It stops working when several teams share three separate API Connect instances with two catalogs each: nobody knows what is live where, changes cannot be reviewed before they hit a gateway, breaking changes slip through, and the instances drift apart.

GitOps turns this around. The Git repository is the catalog. Every API and every Product is a YAML file. A change is a pull request that is validated automatically. When it is merged, a pipeline logs in to the right instance with the apic toolkit and publishes exactly what is in Git.

The three design decisions

QuestionDecisionWhy
Should Products (plans, rate limits, visibility) be managed in Git too, or left to API Manager's auto-publish? Yes, always. Every API sits next to a Product file that references it. The pipeline publishes Products, never bare APIs. In API Connect v10 an API is only reachable on the gateway through a Product published to a Catalog, and the toolkit has no apis:publish — products:publish is the only publish command. Auto-publish creates opaque products you do not control.
Publish on pull request or on merge? PR = validate only; merge = publish. PR builds never write to API Connect. Two open PRs touching the same product would fight over the same name:version in a shared catalog. Validation is enough to give fast feedback; publishing belongs to the merged, reviewed state.
How to promote dev → test → prod when every environment is a separate instance? One folder per environment inside each project (dev/, test/, prod/), promotion = a pull request that copies the folder. Catalog-specific values stay inside the file. Environments run different versions at different times, so the repository must be able to say “test has 1.1.0, prod has 1.0.0”. A folder per environment makes that visible and reviewable. Branch-per-environment would need cherry-picks; a single file for all environments could not express version skew. The two catalogs of an instance always hold the same files, so they share one folder.
Principles that follow from this
  • Git is the single source of truth; API Manager becomes read-only for humans (viewer roles). Only the pipeline identities publish.
  • Drafts in API Manager are not used at all — the PR is the draft.
  • Files are byte-identical across environment folders; only the version present differs. Nobody hand-edits test/ or prod/.
  • The pipeline never deletes, deprecates or retires anything. Removing an API from a gateway is a deliberate manual step.
  • A breaking change is not forbidden — it just has to arrive as a new major version that coexists with the old one.

The four validation stages (fail fast, in this order)

1YAML syntax

Can the file be parsed at all? Tabs, duplicate keys, bad indentation.
yamllint

2OpenAPI validity

Is it a valid OpenAPI 3.0 document, and does it follow the APIC house rules?

3APIC validity

Would API Connect accept the Product and its APIs (IBM extensions, assembly)?
apic validate

4Compatibility

Does the new contract break existing consumers of that environment without a major bump?
oasdiff

What is published, exactly?

Only what changed, per environment folder. Each of the five catalogs remembers the last commit it received through a Git tag (published/dev, published/integ, published/nightly, published/rc, published/prod). The change set for a stage is “every product under projects/*/<env>/ touched since its tag”. A stage with nothing new is skipped, so approvers are never asked to approve an empty publish. The very first run (no tags yet) publishes every folder — the bootstrap.

3. API Connect concepts you need

Five objects matter for this pipeline. If you are new to API Connect, this page is enough to follow the rest of the document.

APIAn OpenAPI 3.0 document plus IBM extensions (x-ibm-configuration) describing how the gateway enforces and routes it. Identified by x-ibm-name:version.
⊂
ProductBundles one or more APIs and defines Plans (rate limits, approval). It is the unit consumers subscribe to and the unit the pipeline publishes. Identified by name:version.
→
CatalogA deployment target inside a provider organization, bound to a gateway service. Here: one or two per project per instance.
→
InstanceA complete API Connect installation (management, gateway, portal). You have three; each has its own URL, org and credentials.
TermWhat it means for you
Instance / environmentdev, test or prod cluster. Selected by the pipeline stage; credentials come from the variable group apic-<env>. The repository folder projects/<project>/<env>/ says what the instance should have.
Provider organizationThe top-level container inside an instance. One per instance; its name is that instance's APIC_ORG.
CatalogA stage: <project>-dev, -integ, -nightly, -rc or <project>. Whatever is published in a catalog is live on its gateway.

The one rule people forget Changing x-ibm-name makes API Connect see a new API; the old one stays published until someone retires it. Treat x-ibm-name as permanent, and use info.version to evolve.

4. Repository layout

APIConnect-catalog/ ├── .azure-pipelines/ │ ├── apic-ci.yml the pipeline: validate → 5 publish stages in 3 independent chains │ └── templates/ │ ├── install-tools.yml tooling; online (hosted agent) or offline (on-prem agent) │ └── publish-stage.yml one deployment stage per catalog ├── config/ │ ├── environments.yml instances, stages, catalog-name patterns — the scripts read this │ ├── .yamllint.yml stage 1 rules │ ├── spectral.yml stage 2 rules: OpenAPI 3.0 + APIC house rules │ └── compat-ignore.txt stage 4 reviewed exceptions ├── scripts/ what the pipeline runs — also runnable on a laptop ├── tools/ install-offline.sh installs the bundled binaries on an on-prem agent ├── docs/ this guide (HTML source + PDF) └── projects/ └── <project>/ one folder per team / product area = ownership + catalog-name prefix ├── project.yaml optional: owner, catalog-name overrides ├── dev/ what the dev instance should have │ ├── apis/<api>.yaml OpenAPI 3.0.x + x-ibm-configuration │ └── products/<product>.yaml plans, rate limits, visibility; apis.*.$ref → ../apis/<api>.yaml ├── test/ same structure — what the test instance should have └── prod/ same structure — what the prod instance should have

Why this shape

  • Project folder = catalog prefix. projects/orders/ publishes to orders-dev, orders-integ, orders-nightly, orders-rc and orders. If a catalog is named differently, declare it in project.yaml.
  • Environment folder = deployed version. Looking at projects/orders/prod/ answers “what does prod have?” without opening API Manager.
  • apis/ and products/ side by side so a Product references its APIs with an obvious relative $ref (../apis/orders.yaml) and the pipeline can map a changed API to the Product that must be republished.
  • No cross references. A Product may only reference APIs in the same <project>/<env>/apis/. Stage 3 rejects anything else, so an environment folder is always self-contained and publishable on its own.

5. Life of a change — from a dev edit to production

#Who / whatWhat happens
1DeveloperCreates a branch, edits projects/orders/dev/apis/orders.yaml (say, adds an optional query parameter and bumps to 1.1.0), bumps the product version in dev/products/orders.yaml, opens a pull request to main.
2Pipeline · validateComputes the change set against origin/main: the changed API and the Product(s) in dev/ that $ref it. Runs stages 1 → 4. Stage 4 compares the file with its version on main.
3Pull requestThe pipeline is a required status check. A red check blocks the merge; annotations point at file and line. The developer fixes and pushes; the pipeline reruns.
4ReviewerReviews the diff like any code. Approves. Merge to main.
5Pipeline · validate (main)Same four stages, now per environment against each environment's last-published tag. Flags which of the five stages have something new: here dev and integ.
6Pipeline · publish_devLogs in to the dev instance, recomputes the change set since published/dev, runs the compatibility check against the live orders-dev catalog, publishes, verifies state: published, moves the tag.
7Approver / publish_integEnvironment apic-integ asks for approval. Same procedure into orders-integ, tag published/integ.
8DeveloperWhen integration testing is done: scripts/promote.sh orders dev test. The script copies dev/ over test/ and prints the diff (1.0.0 → 1.1.0). Commit on a branch, open a promotion PR.
9Pipeline · validate (PR)Stage 4 now compares test/apis/orders.yaml as it was (1.0.0, what the test instance has) with the promoted 1.1.0 — the compatibility question is asked again for the test consumers. Reviewer approves, merge.
10Pipeline · publish_nightly → publish_rcLogs in to the test instance; orders-nightly automatically, orders-rc after approval. The dev chain is skipped — nothing under dev/ changed.
11Developer / Approverscripts/promote.sh orders test prod, PR, merge. publish_prod waits for approval, logs in to the prod instance, publishes to orders.
What if nothing under projects/ changed? The validate stage reports “no API/product changes detected”, skips stages 1–4 and every publish stage is skipped. Changing only scripts or configuration therefore never touches API Connect.
What if two merges happen back-to-back? The second run's change set includes everything since the tag, so it cannot “miss” the first merge. The Exclusive lock check on the Environments serialises publishes so two runs never publish into the same catalog concurrently.

6. The four validation stages

StageTool & commandWhat it catchesHow a failure looks
1 YAML yamllint -c config/.yamllint.yml Tabs, duplicate keys, broken indentation, unquoted special characters — anything that stops a parser before it even sees your API. One annotation per finding with file, line and column.
2 OpenAPI spectral lint -r config/spectral.yml Invalid OpenAPI 3.0 structure (unknown fields, bad $ref, missing responses) plus the APIC house rules: x-ibm-name, semver, single server, enforced, gateway type, no callbacks/links. Annotations per rule with the rule name (e.g. apic-semver-version) and a JUnit report in the Tests tab.
3 APIC apic validate <product.yaml> Repository policy first (relative $ref, file exists, same project and environment folder). Then the IBM toolkit validates the Product and every referenced API offline: IBM extensions, assembly policies, plan structure. The toolkit's message, with the product file annotated.
4 Compat oasdiff breaking <baseline> <new> Contract changes that would break an existing consumer (section 7). Baseline per environment folder: the file at the environment's last publish (PR: on the target branch), or the version live in the target catalog (before publish). A list of breaking changes (rule id, method, path) and one error annotation on the API file.

7. Backward compatibility and versioning policy

Stage 4 is the gate that protects the consumers of your APIs — in each environment. It uses oasdiff, which understands OpenAPI 3.0 and ignores the x-ibm-* extensions, so changing an assembly policy or a backend URL is never mistaken for a contract change.

What counts as what

ClassExamplesOutcome
Breaking Remove or rename a path, operation, request parameter or property · add a required request parameter or property · change a type or format · narrow an enum a client sends · remove a response property, status code or media type · tighten security · change the base path Fails — unless info.version MAJOR was bumped
Potentially breaking New response status code · new enum value in a response · marking an operation deprecated · loosening response constraints Reported, does not fail
Non-breaking New path or operation · optional request parameter or property · new response property · widening an enum a client sends · descriptions, examples, tags · anything under x-ibm-configuration Passes

How the version number drives the pipeline

Non-breaking changeKeep the version or bump MINOR/PATCH. Same product version. The pipeline republishes in place; existing subscriptions keep working.
vs
Breaking changeBump the API MAJOR (1.4.2 → 2.0.0) and the product version. The pipeline publishes a new product version that coexists with the old one. Consumers migrate on their schedule.

Stage 4 compares against the latest published version with the same MAJOR. A new MAJOR therefore has no baseline to break and is allowed through (the differences are still printed for the reviewer). Because the check runs per environment folder, a promotion PR asks the question again for the target environment's consumers: 1.0.0 → 1.1.0 may be fine in dev and still be flagged in prod if prod skipped a step.

Exceptions

Sometimes a change that oasdiff calls breaking is acceptable — an endpoint nobody ever subscribed to, or a field documented as internal. Add a line to config/compat-ignore.txt in the same pull request, as specific as possible (method, path, fragment of the message), with the justification in the PR description. The exception is then reviewed together with the change, and is visible in history forever.

Do not work around the gate by renaming x-ibm-name. That creates a second API and leaves the first one live and unmanaged.

8. Publishing — five stages, three independent chains

After a merge to main, the pipeline runs three chains that do not wait for each other, because they publish different folders to different instances:

ChainFolderStage → catalogGate
devprojects/*/dev/publish_dev → <project>-dev
publish_integ → <project>-integ		automatic
approval on Environment apic-integ, after publish_dev succeeded or was skipped
testprojects/*/test/publish_nightly → <project>-nightly
publish_rc → <project>-rc		automatic
approval on apic-rc, after publish_nightly
prodprojects/*/prod/publish_prod → <project>approval on apic-prod

A stage runs only when the validate stage found something new for it (flag changes.<stage>); otherwise it is Skipped, and a skipped first stage does not block the second one — integ may still have last week's unapproved change to publish.

Inside a publish stage

  1. Tools. Online agents download them; offline agents must already have them (section 12).
  2. Instance credentials. credentials.json of this instance from the Secure File apic-toolkit-credentials-<env>.json → apic client-creds:set.
  3. Login. apic iam-apikey --server $APIC_SERVER --apiKey $APIC_APIKEY with the variable group apic-<env>, followed by a read-only catalogs:list as a smoke test that also proves the org and the instance are the right ones.
  4. Change set. Products under projects/*/<env>/ touched since this stage's published/<stage> tag.
  5. Live compatibility check. Stage 4 again, but the baseline is fetched from each product's target catalog with apic apis:get. This catches drift caused by anyone who published outside Git.
  6. Publish. For each Product: catalog = pattern from config/environments.yml with the project name (or the project.yaml override); apic products:publish --catalog <catalog> <product.yaml> (with --migrate_subscriptions when the version already exists); then products:get must report state: published.
  7. Mark. Move the published/<stage> tag to this commit and push it.
  8. Always. Publish logs as a build artifact; apic logout.

Why tags instead of “publish what this run validated”?

Because stages fail and wait independently. If rc approval is postponed for a week while test/ receives three more promotions, the rc stage must publish the union of those changes, not just the last one. Diffing against the stage's own tag gives exactly that, with no bookkeeping outside Git. A missing tag means “never published from Git” and selects every product of the folder — which is also how you bootstrap a new instance.

Rolling back

  • Non-breaking regression in test or prod: the previous version is still in the lower environment folder or in Git history — restore the file in the environment folder (a PR), or run the pipeline for an earlier commit (Run pipeline → select commit).
  • After a major version: apic products:replace back to the previous product version on that instance, then retire the new one.

9. Promotion by pull request — dev → test → prod

A promotion is nothing more than “make the test/ folder look like the dev/ folder”. The helper does the copy so that nobody edits test/ or prod/ by hand, and prints what is about to change:

$ scripts/promote.sh orders dev test
[12:14:41] Copied 2 file(s): projects/orders/dev -> projects/orders/test
  product orders                         1.1.0
  api     orders-api                     1.1.0
 projects/orders/test/apis/orders-api.yaml      | 16 +++++++++++++++-
 projects/orders/test/products/orders.yaml      |  2 +-
Next: review 'git diff -- projects/orders/test', commit on a branch, open a pull request. Merging publishes to: nightly rc

$ git checkout -b promote/orders-1.1.0-test
$ git commit -am "promote orders 1.1.0 dev -> test"
$ git push -u origin HEAD          # then open the PR

What the PR shows and checks

  • The diff between what test has today and what it will have — reviewable like any code change.
  • Stage 4 with the test baseline: the compatibility question for test's consumers, independent of what happened in dev.
  • Files that exist only in the target are kept and listed (use --prune to remove them). Remember that deleting a file never removes anything from API Connect.

Rules of the road

RuleWhy
Promote whole project folders, never single filesA Product and its APIs move together; a half-promoted folder fails stage 3 or publishes an inconsistent product.
Promote in order: dev → test → prodThe compatibility gate and the human review happen for each environment's consumers. Skipping test means prod gets a change nobody tested against its predecessor.
Never hand-edit test/ or prod/Environment differences belong inside the file (section 10). Hand edits create drift that the next promotion silently overwrites.
Hotfix in prod?Fix in dev/, promote through test with two quick PRs. If you truly must jump, promote dev → prod directly and back-fill test right after — the gate still runs against prod's baseline.
Can dev run ahead of prod for a long time? Yes — that is the point of environment folders. dev/ can be at 2.0.0 while prod/ stays at 1.4.2 for months. When 2.0.0 is promoted, prod receives a new product version next to the old one (section 7), and the old one is retired by hand later.

10. One file, five catalogs — catalog-specific properties

The backend URL, timeouts, or a header value differ between the five catalogs. Instead of editing the file per environment you declare a property with a default and override it per catalog name. The gateway substitutes $(property) at runtime with the value for the catalog it is running in — whichever instance that catalog lives on.

x-ibm-configuration:
  enforced: true
  gateway: datapower-api-gateway
  properties:
    target-url:
      value: https://orders-dev.internal.example.com      # default
      description: Backend base URL
  catalogs:                                                # overrides, keyed by the project's catalog names
    orders-dev:     { properties: { target-url: https://orders-dev.internal.example.com } }
    orders-integ:   { properties: { target-url: https://orders-integ.internal.example.com } }
    orders-nightly: { properties: { target-url: https://orders-nightly.internal.example.com } }
    orders-rc:      { properties: { target-url: https://orders-rc.internal.example.com } }
    orders:         { properties: { target-url: https://orders.internal.example.com } }
  assembly:
    execute:
      - invoke:
          version: 2.0.0
          target-url: $(target-url)$(request.path)          # resolved on the gateway

Because every catalog's value travels inside the file, promote.sh is a pure copy, the folders stay byte-identical apart from the version being promoted, and the compatibility gate never sees an environment difference as a contract change (everything under x-ibm-configuration is ignored by oasdiff).

Verify once per instance Catalog-specific property overrides are an API Connect feature of the API definition. Publish the sample to -dev and -integ and confirm the invoke target differs before relying on it for prod. Alternative if needed: define the property at catalog level in API Manager (Catalog settings → Properties) on each instance and reference it the same way.

What must never differ between catalogs

  • Paths, parameters, schemas — the contract. If test and prod need different contracts they are different major versions.
  • Security schemes. A prod-only header requirement would be invisible to the compatibility gate in dev.
  • Product plans and rate limits — they are part of the reviewed artifact. If prod needs stricter limits, that is a product change reviewed in a PR and promoted like everything else.

Rotation

IBM Cloud API keys do not expire unless you set a lifetime. Decide a rotation cadence (e.g. yearly), rotate in Key Vault, and let the next run pick it up — nothing in the repository changes. If an instance instead requires a toolkit API key created with apic api-keys:create, it carries a ttl: put the expiry in a calendar, because an expired key fails the login step with an unhelpful message.

12. Setting up an on-prem agent from the offline bundle

The bundle ships everything the pipeline needs on a Linux x64 agent that has no internet access, except the IBM toolkit (licensed, downloaded from your own instances). One agent serves all three instances — it only needs network access to their management endpoints.

APIConnect-catalog-bundle-<date>/ ├── repo/ the repository, ready to push to your on-prem Git server ├── APIConnect-catalog.gitbundle the same repository with history: git clone APIConnect-catalog.gitbundle ├── tools/ │ ├── install-offline.sh installer (also in repo/tools/) │ └── linux-x64/ │ ├── bin/ yq · oasdiff · jq · spectral static binaries; spectral is standalone (no Node.js) │ ├── wheels/ yamllint · pyyaml · pathspec for CPython 3.9 – 3.14, pip --no-index │ ├── SHA256SUMS verified by the installer │ └── MANIFEST.txt versions and sources └── docs/ guide.pdf · guide.html

Steps

  1. Prepare the machine. Linux x64 with bash 5, git 2.x, GNU coreutils, Python 3.9+ with pip, and the Azure DevOps agent installed as a dedicated user. Outbound access to the three management endpoints.
  2. Install the bundled tools. 
    unzip APIConnect-catalog-bundle-*.zip && cd APIConnect-catalog-bundle-*
sudo bash tools/install-offline.sh              # verifies SHA256SUMS, installs to /usr/local/bin, pip installs yamllint
  3. Install the IBM toolkit. In API Manager (any instance; use the highest fix pack if they differ) click Tools for download, download the Linux CLI. 
    sudo install -m 0755 apic-slim /usr/local/bin/apic    # or `apic` if you downloaded CLI + Designer
apic --accept-license version                         # must match the instances, 10.0.8.x
  4. Verify as the agent user. for t in yamllint spectral yq oasdiff jq apic git realpath; do command -v $t; done — every line must print a path.
  5. Push the repository to your on-prem Git (Azure Repos or GitHub Enterprise): git clone APIConnect-catalog.gitbundle APIConnect-catalog, add the remote, push main.
  6. Tell the pipeline it is offline. In variable group apic-shared set TOOLS_MODE = offline. The tooling step then only checks that the tools exist and never reaches the internet; a missing tool fails the job with a clear message.
  7. Point the pipeline at your pool. Replace vmImage: ubuntu-latest with name: <your agent pool> in apic-ci.yml and templates/publish-stage.yml.
Updating tools later Rebuild the bundle on a connected machine (same layout, regenerate SHA256SUMS), copy it over, rerun the installer. Versions are listed in MANIFEST.txt; the pipeline prints the versions it found at the start of every job.

4Secure files apic-toolkit-credentials-dev.json, -test.json, -prod.jsonPipelines → Library → Secure files. Upload each instance's credentials.json. Authorize the pipeline.
5Environments apic-dev, apic-integ, apic-nightly, apic-rc, apic-prodPipelines → Environments. Add Approvals (the people allowed to promote) and Exclusive lock on apic-integ, apic-rc and apic-prod; optionally on the others.
6Agent poolSelf-hosted pool with the prepared Linux agent (section 12), or Microsoft-hosted ubuntu-latest with TOOLS_MODE=online and the toolkit as a Universal Package in an Artifacts feed.
7Repository permissionsThe build identity (Project Collection Build Service or the project's build service) needs Contribute and Create tag on the repository so published/<stage> tags can be pushed.
8Catalogs (API Connect side)On each instance, create the catalogs the pattern expects: <project>-dev and -integ on dev, -nightly and -rc on test, <project> on prod, each bound to the gateway service. Different names → projects/<project>/project.yaml.

First run

  1. Open a pull request that touches only the sample project (e.g. edit a description in dev/). Confirm the four stages run and the check turns green.
  2. Merge. Watch publish_dev: it should report “No tag published/dev yet: bootstrapping”, publish every product of dev/ to example-project-dev, and create the tag. publish_nightly and publish_prod bootstrap their folders in the same run; integ, rc and prod wait for approval.
  3. In each API Manager, open the catalog and confirm the product is Published. Call the API through the gateway.
  4. Approve the gated stages when you are ready. Each creates its own tag.
  5. Delete projects/example-project in a PR once your first real API is in. Remember: deleting the files does not remove the products from the five catalogs — retire the sample product by hand.

14. Day-2 operations

Add a new API

  1. Create projects/<project>/dev/apis/<api>.yaml — OpenAPI 3.0.x with info.x-ibm-name, semver info.version, a single servers[].url and an x-ibm-configuration block with catalogs.* overrides for all five catalog names. Copy the sample as a starting point.
  2. Either add it to an existing Product in dev/products/ (apis: { <api>: { $ref: ../apis/<api>.yaml } }) or create a new Product there.
  3. Open a PR. Stage 4 reports “NEW … no baseline” and passes. Merge → -dev; approve → -integ.
  4. Promote to test and prod when ready (section 9).

Add a new project

Create the five catalogs on the three instances (or declare different names in project.yaml), then add projects/<project>/dev/{apis,products}/. test/ and prod/ appear with the first promotion.

Make a non-breaking change

Edit in dev/, optionally bump MINOR/PATCH, open a PR. The Product is republished in place in -dev/-integ; promote when ready.

Make a breaking change

  1. In dev/, bump the API info.version MAJOR (e.g. 2.0.0) and the Product info.version. Consider a new product file if the old version must stay available for a long time.
  2. PR → stage 4 prints the breaking changes but passes because MAJOR changed. Merge, approve.
  3. Promote through test and prod. In each catalog both versions are now live. Communicate the deprecation; when consumers have moved, migrate remaining subscriptions (apic products:replace / supersede) and retire the old version manually, instance by instance.

Change plans or rate limits

Edit the Product file in dev/ only, then promote. It is republished in place; the gateway applies the new limits.

Add a compatibility exception

Add one line to config/compat-ignore.txt in the same PR as the change, matching the oasdiff message as specifically as possible (method + path + text fragment). Explain why in the PR.

Retire an API or Product (manual, by design)

  1. Remove the files from the environment folders in PRs (usually dev first, prod last). The pipeline warns “Deleted in Git but NOT removed from APIC”.
  2. On each instance, in API Manager or with the toolkit: deprecate → retire → delete the product version, per catalog.

Roll back

Restore the previous file in the environment folder via a PR (it is in Git history: git checkout <commit> -- projects/orders/prod), or Run pipeline → select an earlier commit. For a major version, products:replace back and retire the newer version.

Upgrade an instance / the toolkit

After an instance upgrade, download the matching CLI, install it on the agent (offline) or publish it to the Artifacts feed (online) and bump APIC_TOOLKIT_VERSION. If instances are temporarily on different fix packs, use the toolkit of the highest one and check the versions step in the first run against each instance.

15. Troubleshooting — reading a failed run

SymptomMeaning and fix
“No API/product changes detected” and everything skippedOnly files outside projects/ changed, or files outside <project>/<env>/{apis,products}/ (they are ignored with a log line). Expected.
A publish stage shows SkippedIts environment folder has nothing new since published/<stage>. Expected — e.g. a promotion to test skips the dev chain.
Stage 1 found character '\t' that cannot start any tokenA tab in the YAML. Replace with spaces.
Stage 2 apic-x-ibm-name / apic-semver-versionAdd info.x-ibm-name (lowercase slug) or make info.version MAJOR.MINOR.PATCH.
Stage 2 apic-single-serverOnly one servers[] entry is allowed; its path is the base path.
Stage 3 “must use a relative $ref …”The Product references an API by name:version. Use $ref: ../apis/<file>.yaml.
Stage 3 “points outside projects/…/test/apis/ (cross-project / cross-environment …)”A Product in one environment folder references an API in another. Each folder must be self-contained; run promote.sh instead of hand-linking.
Stage 3 apic validate error textIBM extension or assembly problem; the message is the toolkit's. Run apic validate <product> locally to iterate quickly.
Stage 4 “BREAKING change … without a MAJOR version bump” on a promotion PRThe target environment's consumers would break: the version now in test/ or prod/ is not compatible with the one that was there. Promote a MAJOR version instead, or add a reviewed exception (section 7).
Stage 4 “oasdiff failed (exit 2)”oasdiff could not load one of the specs — usually a $ref to a missing component. Fix the spec; stage 2 normally catches this first.
Publish: “offline mode: 'X' is not installed on this agent”Run tools/install-offline.sh on the agent, or install the toolkit; check PATH for the agent user.
Publish: login failsCheck APIC_SERVER of that instance, that the API key's service ID is a member of that instance's provider org, and that the key is not expired. Try the same command interactively from the agent.
Publish: catalogs:list works but publish says catalog not foundThe catalog name derived from the project folder (<project>-integ etc.) does not exist on that instance. Create it, or declare the real name in projects/<project>/project.yaml.
Publish: “Refusing to publish: … is not under projects/<project>/prod/products/”Safety guard: a stage only publishes its own environment folder. Should not happen from the pipeline; happens when running publish.sh by hand with the wrong list.
Publish: live compatibility check fails but the PR passedWhat is live in the catalog differs from what Git thinks — someone published outside Git on that instance. Reconcile: export the live definition, compare, decide, then republish from Git.
Publish: “ended in state 'staged'/'pending'”The product uploaded but did not activate. Check the catalog's gateway service and any approval/task settings in Catalog settings on that instance.
Publish: git push … refs/tags/published/… permission deniedGrant the build identity Contribute + Create tag. The publish itself already happened; rerun the stage to set the tag.
Publish to <project> (prod) rejected for an existing versionThe prod catalog may be in Production mode, which can block republishing the same version. Either disable it or adopt “every prod change bumps the version + products:replace”.

16. Before the first publish — items to verify on each instance

The pipeline uses commands documented for the v10.0.8 toolkit. A few behaviours depend on your installations and were flagged in the design; check them once per instance from a laptop with the toolkit installed.

CheckHow
☐Non-interactive login works on dev, test and prodapic iam-apikey --server <mgmt> --apiKey <IBM Cloud API key> then apic catalogs:list --server … --org …. If an instance only accepts IBMid/OIDC, switch the login step to apic login --server … --sso --context provider --apiKey <toolkit key from apic api-keys:create>.
☐Catalog namesapic catalogs:list on each instance shows <project>-dev/-integ, -nightly/-rc, <project> — or you have written the real names into project.yaml.
☐Shape of apis:get outputapic apis:get --scope catalog <name>:<version> --catalog <project>-dev --org … --server … --format yaml --output -. The script accepts the bare definition or an envelope with .api; look at the first live-compat log.
☐Shape of apis:list --format jsonExpected { "results": [ … ] }; the script also accepts a bare array.
☐apic validate exit codeBreak a sample on purpose; the command must exit non-zero. The script additionally counts “Validated” lines.
☐--migrate_subscriptions on republishRepublish an existing version in <project>-dev with a test subscription and confirm it survives.
☐Catalog-specific properties resolvePublish the sample to -dev and -integ; the invoke target must differ.
☐Production mode on the prod catalogsCatalog settings on the prod instance. Decide the policy (section 15, last row).
☐Gateway OpenAPI 3.0 subsetOptionally run apic draft-apis:validate online in <project>-dev for one representative API.
☐Toolkit version vs. instance versionsapic version against each management endpoint; if fix packs differ, use the highest toolkit and test publish on the lowest instance.
☐Existing content in the catalogsAnything published today that is not in Git will be flagged as drift by the live check, or silently replaced if a product with the same name:version is in Git. Export or retire it first (your manual “start clean”).
