1. Why this exists — the problem and the three decisions

Publishing APIs to API Connect by hand — editing drafts in API Manager and pressing Publish — works for one team and a handful of APIs. It stops working when several teams share an environment: nobody knows what is live, changes cannot be reviewed before they hit the gateway, breaking changes slip through, and dev, test and prod drift apart.

GitOps turns this around. The Git repository is the catalog. Every API and every Product is a YAML file. A change is a pull request that is validated automatically. When it is merged, a pipeline logs in with the apic toolkit and publishes exactly what is in Git — first to dev, then, after approval, to test and prod.

The three design decisions

QuestionDecisionWhy
Should Products (plans, rate limits, visibility) be managed in Git too, or left to API Manager's auto-publish? Yes, always. Every API sits next to a Product file that references it. The pipeline publishes Products, never bare APIs. In API Connect v10 an API is only reachable on the gateway through a Product published to a Catalog, and the toolkit has no apis:publish — products:publish is the only publish command. Auto-publish creates opaque products you do not control.
Publish on pull request or on merge? PR = validate only; merge = publish. PR builds never write to API Connect. Two open PRs touching the same product would fight over the same name:version in a shared catalog. Validation is enough to give fast feedback; publishing belongs to the merged, reviewed state.
How to promote dev → test → prod: branches, folders or configuration? Configuration. One main branch, one file per API, environment differences expressed inside the file. A branch per environment drifts and needs cherry-picks; a folder per environment duplicates every file. With configuration, test and prod receive byte-identical artifacts and the pipeline stage decides the target catalog.
Principles that follow from this
  • Git is the single source of truth; API Manager becomes read-only for humans (viewer roles). Only the pipeline identity publishes.
  • Drafts in API Manager are not used at all — the PR is the draft.
  • The pipeline never deletes, deprecates or retires anything. Removing an API from the gateway is a deliberate manual step.
  • A breaking change is not forbidden — it just has to arrive as a new major version that coexists with the old one.

2. The big picture — from pull request to production

Everything starts with a developer editing a YAML file. The diagram shows the whole path.

→

→
3 · Review & mergeGreen check + human review. Merge to main.
→
4 · Publish devAutomatic. Changed products are published to catalog dev.
→
5 · Publish testWaits for approval. Same commit, catalog test.
→
6 · Publish prodWaits for approval. Same commit, catalog prod.

The four validation stages (fail fast, in this order)

1YAML syntax

Can the file be parsed at all? Tabs, duplicate keys, bad indentation.
yamllint

2OpenAPI validity

Is it a valid OpenAPI 3.0 document, and does it follow the APIC house rules?
spectral

3APIC validity

Would API Connect accept the Product and its APIs (IBM extensions, assembly)?
apic validate

4Compatibility

Does the new contract break existing consumers without a major version bump?
oasdiff

If a stage fails, the later ones do not run: the developer sees the first real problem, not a wall of consequences. All findings appear as annotations on the build and as test results in the pull request's Checks tab.

What is published, exactly?

Only what changed. The pipeline computes a change set: every Product file that was modified, plus every Product that references a modified API file. Each environment remembers the last commit it received through a Git tag (published/dev, published/test, published/prod); the change set for an environment is “everything since its tag”. That is why a failed prod publish on Monday is simply picked up by Tuesday's run, and why the very first run (no tags yet) publishes the whole repository — the bootstrap.

Where does the environment-specific configuration go? Inside the API file, under x-ibm-configuration.catalogs.<catalog>.properties. The gateway resolves the value for the catalog it runs in, so one file serves dev, test and prod (section 9).

3. API Connect concepts you need

Four objects matter for this pipeline. If you are new to API Connect, this page is enough to follow the rest of the document.

APIAn OpenAPI 3.0 document plus IBM extensions (x-ibm-configuration) describing how the gateway enforces and routes it. Identified by x-ibm-name:version.
⊂
ProductBundles one or more APIs and defines Plans (rate limits, approval). It is the unit consumers subscribe to and the unit the pipeline publishes. Identified by name:version.
→
CatalogA deployment target inside your provider organization, bound to a gateway service. Here: dev, test, prod — one per environment.
→
GatewayThe DataPower API Gateway that serves the traffic. Whatever is published in a catalog is live on its gateway.
TermWhat it means for you
Provider organizationYour tenant's top-level container. There is exactly one; its name is the APIC_ORG variable.
CatalogEnvironment. The pipeline stage chooses the catalog; the folder structure never encodes it.
SpaceAn optional sub-partition of a catalog with its own permissions. Not used today. If enabled later, each projects/<name> folder maps to a Space.
PlanPart of a Product: rate limits and whether subscriptions need approval. Consumers subscribe to a plan.
Publish vs. stagePublishing makes a product live on the gateway. Staging uploads it without activating it. This pipeline always publishes.
RepublishPublishing a product name:version that already exists updates it in place; subscriptions are kept. Used for non-breaking changes.
Replace / supersedeToolkit operations that move subscriptions from an old product version to a new one. Used manually after a breaking (major) change.
The one rule people forget Changing x-ibm-name makes API Connect see a new API; the old one stays published until someone retires it. Treat x-ibm-name as permanent, and use info.version to evolve.

4. Repository layout

APIConnect-catalog/ ├── .azure-pipelines/ │ ├── apic-ci.yml the pipeline: validate → publish dev → test → prod │ └── templates/ │ ├── install-tools.yml tooling; online (hosted agent) or offline (on-prem agent) │ └── publish-stage.yml one deployment stage per catalog ├── config/ │ ├── .yamllint.yml stage 1 rules │ ├── spectral.yml stage 2 rules: OpenAPI 3.0 + APIC house rules │ └── compat-ignore.txt stage 4 reviewed exceptions ├── scripts/ what the pipeline runs — also runnable on a laptop ├── tools/ │ └── install-offline.sh installs the bundled binaries on an on-prem agent ├── docs/ this guide (HTML source + PDF) └── projects/ └── <project>/ one folder per team / product area = ownership boundary ├── apis/ │ └── <api>.yaml OpenAPI 3.0.x + x-ibm-configuration, one file for all environments └── products/ └── <product>.yaml plans, rate limits, visibility; apis.*.$ref → ../apis/<api>.yaml

Why apis/ and products/ are separate folders

  • A Product must reference its APIs with a relative $ref. Putting APIs in a sibling folder makes the reference obvious (../apis/orders.yaml) and lets the pipeline map a changed API to the Product that must be republished.
  • Both are YAML; the folder tells the pipeline (and the reader) which is which without inspecting content.
  • Cross-project references are rejected: a Product can only bundle APIs from its own project. Ownership stays clean.

5. Life of a change — step by step

#Who / whatWhat happens
1DeveloperCreates a branch, edits projects/orders/apis/orders.yaml (say, adds an optional query parameter), opens a pull request to main.
2Pipeline · validateComputes the change set against origin/main: the changed API and the Product(s) that $ref it. Runs stages 1 → 4. Stage 4 compares the file with its version on main.
3Pull requestThe pipeline is a required status check. A red check blocks the merge; annotations point at file and line. The developer fixes and pushes; the pipeline reruns.
4ReviewerReviews the diff like any code. Approves. Merge to main.
5Pipeline · validate (main)Same four stages, now against the published/dev tag — i.e. against what dev currently has.
6Pipeline · publish_devInstalls/finds tools, sets toolkit credentials, logs in with the API key, recomputes the change set since published/dev, runs the compatibility check against the live catalog, then apic products:publish per Product and verifies the state is published. Moves the published/dev tag to this commit. Logs out.
7ApproverAzure DevOps Environment apic-test asks for approval. The approver sees exactly which commit and which products are involved.
8Pipeline · publish_testIdentical to step 6 for catalog test and tag published/test.
9Approver / Pipeline · publish_prodSame again for prod. The artifacts are byte-identical to what was tested.
What if nothing under projects/ changed? The validate stage reports “no API/product changes detected”, skips stages 1–4 and the publish stages publish nothing. Changing only scripts or configuration therefore never touches API Connect.
What if two merges happen back-to-back? The second run's change set includes everything since the tag, so it cannot “miss” the first merge. The Exclusive lock check on the test and prod Environments serialises publishes so two runs never publish concurrently.

6. The four validation stages

StageTool & commandWhat it catchesHow a failure looks
1 YAML yamllint -c config/.yamllint.yml Tabs, duplicate keys, broken indentation, unquoted special characters — anything that stops a parser before it even sees your API. One annotation per finding with file, line and column.
2 OpenAPI spectral lint -r config/spectral.yml Invalid OpenAPI 3.0 structure (unknown fields, bad $ref, missing responses) plus the APIC house rules: x-ibm-name, semver, single server, enforced, gateway type, no callbacks/links. Annotations per rule with the rule name (e.g. apic-semver-version) and a JUnit report in the Tests tab.
3 APIC apic validate <product.yaml> Repository policy first (relative $ref, file exists, same project). Then the IBM toolkit validates the Product and every referenced API offline: IBM extensions, assembly policies, plan structure. The toolkit's message, with the product file annotated.
4 Compat oasdiff breaking <baseline> <new> Contract changes that would break an existing consumer (section 7), compared with the version on main (PR) or the version live in the target catalog (before publish). A list of breaking changes (rule id, method, path) and one error annotation on the API file.

7. Backward compatibility and versioning policy

Stage 4 is the gate that protects the consumers of your APIs. It uses oasdiff, which understands OpenAPI 3.0 and ignores the x-ibm-* extensions — so changing an assembly policy or a backend URL is never mistaken for a contract change.

What counts as what

ClassExamplesOutcome
Breaking Remove or rename a path, operation, request parameter or property · add a required request parameter or property · change a type or format · narrow an enum a client sends · remove a response property, status code or media type · tighten security · change the base path Fails — unless info.version MAJOR was bumped
Potentially breaking New response status code · new enum value in a response · marking an operation deprecated · loosening response constraints Reported, does not fail
Non-breaking New path or operation · optional request parameter or property · new response property · widening an enum a client sends · descriptions, examples, tags · anything under x-ibm-configuration Passes

How the version number drives the pipeline

Non-breaking changeKeep the version or bump MINOR/PATCH. Same product version. The pipeline republishes in place; existing subscriptions keep working.
vs
Breaking changeBump the API MAJOR (1.4.2 → 2.0.0) and the product version. The pipeline publishes a new product version that coexists with the old one. Consumers migrate on their schedule.

Stage 4 compares against the latest published version with the same MAJOR. A new MAJOR therefore has no baseline to break and is allowed through (the differences are still printed for the reviewer). Afterwards, subscriptions are moved with apic products:replace or products:supersede and the old version is retired by hand — that lifecycle is deliberately outside this pipeline.

Exceptions

Sometimes a change that oasdiff calls breaking is acceptable — an endpoint nobody ever subscribed to, or a field documented as internal. Add a line to config/compat-ignore.txt in the same pull request, as specific as possible (method, path, fragment of the message), with the justification in the PR description. The exception is then reviewed together with the change, and is visible in history forever.

Do not work around the gate by renaming x-ibm-name. That creates a second API and leaves the first one live and unmanaged.

8. Publishing and promotion — dev, test, prod

devEnvironment apic-devNo approval. Publishes on every merge to main.Tag: published/dev
testEnvironment apic-testApproval + exclusive lock. Same commit as dev.Tag: published/test
prodEnvironment apic-prodApproval + exclusive lock. Same commit as test.Tag: published/prod

Inside a publish stage

  1. Tools. Online agents download them; offline agents must already have them (section 11).
  2. Toolkit credentials. credentials.json from the Secure File → apic client-creds:set.
  3. Login. apic iam-apikey --server $APIC_SERVER --apiKey $APIC_APIKEY, followed by a read-only catalogs:list as a smoke test. The key comes from a Key Vault-linked variable group and is only ever passed as an environment variable.
  4. Change set. Everything under projects/ that changed since this environment's published/<env> tag → list of Products.
  5. Live compatibility check. Stage 4 again, but the baseline is fetched from the catalog with apic apis:get. This catches drift caused by anyone who published outside Git.
  6. Publish. For each Product: apic products:publish --server … --org … --catalog <env> <product.yaml> (with --migrate_subscriptions when the version already exists), then products:get must report state: published.
  7. Mark. Move the published/<env> tag to this commit and push it.
  8. Always. Publish logs as a build artifact; apic logout.

Why tags instead of “publish what this run validated”?

Because environments fail independently. If prod approval is postponed for a week while dev receives five more merges, the prod stage must publish the union of those changes, not just the last one. Diffing against the environment's own tag gives exactly that, with no bookkeeping outside Git. A missing tag means “never published from Git” and selects every Product — which is also how you bootstrap.

Rolling back

  • Non-breaking regression: run the pipeline for an earlier commit (Run pipeline → select commit) and approve the stages you need. The change set is computed relative to the tag, so the older files are republished in place.
  • After a major version: apic products:replace back to the previous product version, then retire the new one.

9. One definition, three environments — catalog-specific properties

The backend URL, timeouts, or a header value usually differ between dev, test and prod. Instead of three copies of the API you declare a property with a default and override it per catalog. The gateway substitutes $(property) at runtime with the value for the catalog it is running in.

x-ibm-configuration:
  enforced: true
  gateway: datapower-api-gateway
  properties:
    target-url:
      value: https://orders-dev.internal.example.com      # default → used by the dev catalog
      description: Backend base URL
  catalogs:                                                # overrides, keyed by catalog name
    test:
      properties:
        target-url: https://orders-test.internal.example.com
    prod:
      properties:
        target-url: https://orders.internal.example.com
  assembly:
    execute:
      - invoke:
          version: 2.0.0
          target-url: $(target-url)$(request.path)          # resolved on the gateway

Anything under x-ibm-configuration is ignored by the compatibility gate, so switching a backend never counts as a contract change.

Verify once on your tenant Catalog-specific property overrides are an API Connect feature of the API definition. Confirm on dev that the resolved target-url is the override, not the default, before relying on it for prod. Alternative if needed: define the property at catalog level in API Manager (Catalog settings → Properties) and reference it the same way.

What must never differ between environments

  • Paths, parameters, schemas — the contract. If test and prod need different contracts they are different major versions.
  • Security schemes. A prod-only header requirement would be invisible to the compatibility gate on dev.
  • Product plans and rate limits — they are part of the reviewed artifact. If prod needs stricter limits, that is a product change reviewed in a PR.

Rotation

IBM Cloud API keys do not expire unless you set a lifetime. Decide a rotation cadence (e.g. yearly), rotate in Key Vault, and let the next run pick it up — nothing in the repository changes. If your tenant instead requires a toolkit API key created with apic api-keys:create, it carries a ttl: put the expiry in a calendar, because an expired key fails the login step with an unhelpful message.

11. Setting up an on-prem agent from the offline bundle

The bundle ships everything the pipeline needs on a Linux x64 agent that has no internet access, except the IBM toolkit (licensed, downloaded from your own tenant).

APIConnect-catalog-bundle-<date>/ ├── repo/ the repository, ready to push to your on-prem Git server ├── APIConnect-catalog.gitbundle the same repository with history: git clone APIConnect-catalog.gitbundle ├── tools/ │ ├── install-offline.sh installer (also in repo/tools/) │ └── linux-x64/ │ ├── bin/ yq · oasdiff · jq · spectral static binaries; spectral is standalone (no Node.js) │ ├── wheels/ yamllint · pyyaml · pathspec for CPython 3.9 – 3.14, pip --no-index │ ├── SHA256SUMS verified by the installer │ └── MANIFEST.txt versions and sources └── docs/ guide.pdf · guide.html

Steps

  1. Prepare the machine. Linux x64 with bash 5, git 2.x, GNU coreutils, Python 3.9+ with pip, and the Azure DevOps agent installed as a dedicated user.
  2. Install the bundled tools. 
    unzip APIConnect-catalog-bundle-*.zip && cd APIConnect-catalog-bundle-*
sudo bash tools/install-offline.sh              # verifies SHA256SUMS, installs to /usr/local/bin, pip installs yamllint
  3. Install the IBM toolkit. In API Manager click Tools for download, download the Linux CLI and credentials.json. 
    sudo install -m 0755 apic-slim /usr/local/bin/apic    # or `apic` if you downloaded CLI + Designer
apic --accept-license version                         # must match the tenant version, 10.0.8.x
  4. Verify as the agent user. for t in yamllint spectral yq oasdiff jq apic git realpath; do command -v $t; done — every line must print a path.
  5. Push the repository to your on-prem Git (Azure Repos or GitHub Enterprise): git clone APIConnect-catalog.gitbundle APIConnect-catalog, add the remote, push main.
  6. Tell the pipeline it is offline. In variable group apic-shared set TOOLS_MODE = offline. The tooling step then only checks that the tools exist and never reaches the internet; a missing tool fails the job with a clear message.
  7. Point the pipeline at your pool. Replace vmImage: ubuntu-latest with name: <your agent pool> in apic-ci.yml and templates/publish-stage.yml.
Updating tools later Rebuild the bundle on a connected machine (same layout, regenerate SHA256SUMS), copy it over, rerun the installer. Versions are listed in MANIFEST.txt; the pipeline prints the versions it found at the start of every job.

First run

  1. Open a pull request that touches only the sample project (e.g. edit a description). Confirm the four stages run and the check turns green.
  2. Merge. Watch publish_dev: it should report “No tag published/dev yet: bootstrapping”, publish every Product in the repository to dev, and create the tag.
  3. In API Manager, open the dev catalog and confirm the product is Published. Call the API through the gateway.
  4. Approve test, then prod, when you are ready. Each creates its own tag.
  5. Delete projects/example-project in a PR once your first real API is in. Remember: deleting the file does not remove the product from API Connect — retire the sample product by hand.

13. Day-2 operations

Add a new API

  1. Create projects/<project>/apis/<api>.yaml — OpenAPI 3.0.x with info.x-ibm-name, semver info.version, a single servers[].url and an x-ibm-configuration block. Copy the sample as a starting point.
  2. Either add it to an existing Product (apis: { <api>: { $ref: ../apis/<api>.yaml } }) or create a new Product in products/.
  3. Open a PR. Stage 4 reports “NEW … no baseline” and passes. Merge, approve.

Make a non-breaking change

Edit the file, optionally bump MINOR/PATCH, open a PR. The Product is republished in place; subscriptions untouched.

Make a breaking change

  1. Bump the API info.version MAJOR (e.g. 2.0.0) and the Product info.version. Consider a new product file if the old version must stay available for a long time.
  2. PR → stage 4 prints the breaking changes but passes because MAJOR changed. Merge, approve.
  3. Both versions are now live. Communicate the deprecation; when consumers have moved, migrate remaining subscriptions (apic products:replace / supersede) and retire the old version manually.

Change plans or rate limits

Edit the Product file only. It is republished in place; the gateway applies the new limits.

Add a compatibility exception

Add one line to config/compat-ignore.txt in the same PR as the change, matching the oasdiff message as specifically as possible (method + path + text fragment). Explain why in the PR.

Retire an API or Product (manual, by design)

  1. Remove the files in a PR. The pipeline warns “Deleted in Git but NOT removed from APIC”.
  2. In API Manager or with the toolkit: deprecate → retire → delete the product version, per catalog, in the order dev, test, prod.

Roll back

Run pipeline → select an earlier commit, approve the stages you need. For a major version, products:replace back and retire the newer version.

Upgrade the tenant / toolkit

IBM upgrades SaaS tenants on their schedule. After an upgrade, download the matching CLI, install it on the agent (offline) or publish it to the Artifacts feed (online) and bump APIC_TOOLKIT_VERSION. The version step at the start of each job shows what is in use.

14. Troubleshooting — reading a failed run

SymptomMeaning and fix
“No API/product changes detected” and everything skippedOnly files outside projects/ changed. Expected.
Stage 1 found character '\t' that cannot start any tokenA tab in the YAML. Replace with spaces.
Stage 2 apic-x-ibm-name / apic-semver-versionAdd info.x-ibm-name (lowercase slug) or make info.version MAJOR.MINOR.PATCH.
Stage 2 apic-single-serverOnly one servers[] entry is allowed; its path is the base path.
Stage 3 “must use a relative $ref …”The Product references an API by name:version. Use $ref: ../apis/<file>.yaml.
Stage 3 apic validate error textIBM extension or assembly problem; the message is the toolkit's. Run apic validate <product> locally to iterate quickly.
Stage 4 “BREAKING change … without a MAJOR version bump”Either revert the incompatible part, bump MAJOR, or add a reviewed exception (section 7).
Stage 4 “oasdiff failed (exit 2)”oasdiff could not load one of the specs — usually a $ref to a missing component. Fix the spec; stage 2 normally catches this first.
Publish: “offline mode: 'X' is not installed on this agent”Run tools/install-offline.sh on the agent, or install the toolkit; check PATH for the agent user.
Publish: login failsCheck APIC_SERVER, that the API key's service ID is a member of the provider org, and that the key is not expired. Try the same command interactively from the agent.
Publish: live compatibility check fails but the PR passedWhat is live in the catalog differs from what Git thinks — someone published outside Git. Reconcile: export the live definition, compare, decide, then republish from Git.
Publish: “ended in state 'staged'/'pending'”The product uploaded but did not activate. Check the catalog's gateway service and any approval/task settings in Catalog settings.
Publish: git push … refs/tags/published/… permission deniedGrant the build identity Contribute + Create tag. The publish itself already happened; rerun the stage to set the tag.
Publish to prod rejected for an existing versionThe prod catalog may be in Production mode, which can block republishing the same version. Either disable it or adopt “every prod change bumps the version + products:replace”.

15. Before the first publish — items to verify on your tenant

The pipeline uses commands documented for the v10.0.8 toolkit. A few behaviours depend on your tenant and were flagged in the design; check them once from a laptop with the toolkit installed.

CheckHow
☐Non-interactive login worksapic iam-apikey --server <mgmt> --apiKey <IBM Cloud API key> then apic catalogs:list --server … --org …. If the tenant only accepts IBMid/OIDC, switch the login step to apic login --server … --sso --context provider --apiKey <toolkit key from apic api-keys:create>.

☐Shape of apis:list --format jsonExpected { "results": [ … ] }; the script also accepts a bare array.
☐apic validate exit codeBreak a sample on purpose; the command must exit non-zero. The script additionally counts “Validated” lines.
☐--migrate_subscriptions on republishRepublish an existing version in dev with a test subscription and confirm it survives.
☐Catalog-specific properties resolvePublish the sample to dev and test; the invoke target must differ.
☐Production mode on prodCatalog settings. Decide the policy (section 14, last row).
☐Gateway OpenAPI 3.0 subsetOptionally run apic draft-apis:validate online in dev for one representative API.
☐Existing content in the catalogsAnything published today that is not in Git will be flagged as drift by the live check, or silently replaced if a product with the same name:version is in Git. Export or retire it first (your manual “start clean”).
